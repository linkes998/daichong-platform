# 云充站 · 虚拟商品会员代充交易平台 — 项目理解文档

> 生成时间：2026-09-23｜分析范围：`d:/daichong-platform` 全仓库（不含 `shots/` 截图与 `.pb` 二进制）
> 结论一句话：这是一套**零第三方依赖、单进程 Node.js** 实现的「前台商城 + 运营后台 + 上游供货对接」完整业务骨架，支付与上游充值均为**沙箱模拟**，数据落在单个 JSON 文件。

---

## 一、架构概览

### 1.1 技术形态

| 维度 | 事实 |
| --- | --- |
| 语言 / 运行时 | Node.js（CommonJS），无 `package.json`、无 `node_modules`、无构建步骤 |
| 后端 | 原生 `http` 模块手写路由（`server.js`，约 1066 行） |
| 前端 | 原生 HTML + 原生 JS（无框架、无打包），模板字符串渲染 + 全局函数挂载给 `onclick` |
| 样式 | 原生 CSS，`theme.css` 提供设计令牌，`store.css` / `admin.css` 分管前台与后台 |
| 存储 | 单文件 JSON（`data/db.json`），内存态单例 + 原子写入 |
| 外部依赖 | 仅 Node 内置模块：`http` / `https` / `fs` / `path` / `crypto` / `url` / `child_process` |
| 默认端口 | `8899`（`PORT` / `HOST` 环境变量可覆盖） |

### 1.2 分层结构

```
┌──────────────────────────────────────────────────────────────┐
│ 表现层  public/*.html + assets/*.js + assets/*.css            │
│   index(商城) / pay(收银台) / query(查单) / admin(后台)        │
└───────────────▲──────────────────────────┬───────────────────┘
                │ fetch /api/*             │ 静态资源
┌───────────────┴──────────────────────────▼───────────────────┐
│ 接入层  server.js  http.createServer → 静态服务 / handleApi    │
│   工具：readBody / json / ok / fail / auth / tokens(Map)       │
└───────────────▲──────────────────────────┬───────────────────┘
                │                          │
┌───────────────┴──────────┐  ┌────────────▼───────────────────┐
│ 业务编排（均在 server.js）│  │ 适配层 lib/                     │
│  dispatch / scheduleSettle│  │  supplier.js  上游供货 API 适配 │
│  markSuccess / overview   │  │  payment.js   支付网关适配      │
│  decorate / genDemoOrders │  └────────────┬───────────────────┘
└───────────────▲──────────┘               │
                └──────────────┬───────────┘
┌───────────────────────────────▼───────────────────────────────┐
│ 数据层  lib/db.js  内存单例 + 原子写 + 操作日志 + uid 生成     │
│   data/db.json（运行时）  data/seed.json（种子模板）           │
└───────────────────────────────────────────────────────────────┘
```

**关键架构特征**

1. **业务编排全部内联在 `server.js`，而不是独立 service 层**：`dispatch` / `markSuccess` / `overview` 等核心函数直接写在路由文件里，路由与业务强耦合（这是后续最值得重构的点）。
2. **数据层是唯一出口**：`lib/db.js` 暴露 `get()` / `save()`，README 明确「替换成 MySQL/PostgreSQL 成本低」——因为全仓库只有它读写磁盘。
3. **适配层把"外部不确定性"收口**：`supplier.js` 收口上游协议（签名/重试/沙箱），`payment.js` 收口支付网关，两者都提供 `isSandbox` 语义，实现「演示即跑通、生产换配置」。

## 二、数据模型

`data/db.json` 顶层 10 个键（实测：`payMethods=5 categories=9 suppliers=9 products=30 orders=100 logs=160 admins=1`）：

| 集合 | 说明 | 关键字段 |
| --- | --- | --- |
| `settings` | 站点与交易配置 | `siteName/slogan/notice/service/orderExpireMinutes/autoRecharge/sandboxMode/minAmountAlert` |
| `payMethods[]` | 支付方式 | `code, name, icon, enabled, sort, fee` |
| `payConfig` | 支付网关 | `gateway, apiUrl, merchantId, merchantKey, notifyUrl, sandboxMode, autoRefundOnFail` |
| `categories[]` | 前台「服务专区」 | `id, name, icon, desc, sort, status, hue` |
| `suppliers[]` | **商品来源 / 上游通道**（核心） | `mode(api/mock/manual), apiUrl, orderPath, queryPath, method, appId, appSecret, signType, contentType, timeout, retry, markup, priority, balance, mockSuccessRate, mockDelaySec, categories[], status` |
| `products[]` | 商品（含内嵌 `skus[]`） | `id, catId, name, subtitle, icon, hue, tags, badge, sort, status, sales, accountType, accountLabel, accountPlaceholder, accountHint, notice, needConfirm, deliveryMode` |
| `products[].skus[]` | 套餐（价格与库存的最小单位） | `id, name, faceValue, price, cost, stock, supplierId, supplierSku, status, sort` |
| `orders[]` | 订单 | `no, productId/Sku, account, accountType, quantity, price, cost, amount, faceValue, payMethod, status, supplierId, supplierSku, supplierOrderNo, createdAt, expireAt, paidAt, finishedAt, attempts, logs[], payTradeNo, lastUpstreamMessage` |
| `logs[]` | 操作日志（后台展示，最多 800 条） | `id, action, detail, operator, at` |
| `admins[]` | 管理员 | `id, username, password(明文), name, role, lastLogin` |
| `meta` | 元信息 | `createdAt, version, updatedAt` |

**订单状态机**（`server.js:19` 的 `STATUS_TEXT` 是唯一权威定义，前后端共用语义）：

```
pending_payment 待支付 ──支付──▶ paid 已支付·待充值 ──派单──▶ recharging 充值中 ──回调/结算──▶ success 已完成
                                      │                            │
                                      └──────失败──────────────────┴──▶ failed 充值失败 ──退款──▶ refunded 已退款
                                                                        pending_payment/failed ──▶ closed 已关闭
```

> ⚠️ 命名不一致点：订单字段统一用 `skuId`（无 `sku` 前缀歧义），但商品内嵌数组叫 `skus`、供应商侧叫 `supplierSku`，读代码时需注意三种粒度：**product → sku → supplierSku**。

## 三、模块说明与核心逻辑解析

### 3.1 `server.js` — 接入层 + 业务编排层

#### 3.1.1 工具与鉴权

| 函数 | 位置 | 职责 |
| --- | --- | --- |
| `readBody(req)` | `server.js:67` | 统一读请求体；`>2MB` 直接 `req.destroy()`；按 `Content-Type` 走 JSON 或 `URLSearchParams`；JSON 解析失败**静默返回 `{}`** |
| `json/ok/fail` | `server.js:49-65` | 统一响应格式 `{ ok:true, ... }` / `{ ok:false, message }`；`Cache-Control: no-store`，CORS 全开 `*` |
| `serveStatic` | `server.js:91` | 静态文件服务；`path.join` 后做 `startsWith(PUBLIC_DIR)` 前缀校验防目录穿越；无扩展名未命中时**回退 index.html**（伪前端路由） |
| `auth(req)` | `server.js:116` | Bearer Token 校验，命中则**滑动续期 8 小时**；Token 存在**进程内 `Map`**（重启即失效） |
| `pushLog(order,msg,level)` | `server.js:153` | 写订单级处理日志（时间线数据源） |
| `decorate(order)` | `server.js:134` | **装饰器**：补齐 `statusText` / `supplierName` / `grossProfit`，所有对外的订单对象都经过它 |

#### 3.1.2 订单业务核心链路（本项目最关键的 4 个函数）

**① `dispatch(order, opts)` — 派单**（`server.js:159`）

```
attempts++ → resolveSupplier(sku, product) → status='recharging'
  → pushLog「第 N 次提交商品来源」→ db.save()
  → supplier.submitOrder(order, sup)          // 适配层，见 3.2
  ├─ r.ok 且 r.status==='success' → markSuccess(order)          // 上游同步返回成功 → 立即完成
  ├─ r.ok 且非 success            → scheduleSettle(order.no, 延迟) // 上游受理 → 等异步结果
  └─ !r.ok                        → status='failed' + db.addLog
```

**② `scheduleSettle(orderNo, delay)` — 异步结算模拟**（`server.js:198`）
用 `setTimeout` 模拟上游异步回调：以 `md5(order.no + supplierId)` 前 8 字节折算 `[0,1]` 随机数，与 `mockSuccessRate` 比较——**同一订单结果确定可复现**（便于演示与自检）。`manual` 模式直接跳过（必须后台手动完成）。定时器用 `Map` 去重，且 `t.unref()` 不阻塞进程退出。

**③ `markSuccess(order, reason)` — 幂等完成**（`server.js:224`）
`if (order.status === 'success') return;` 保证幂等；随后写 `finishedAt`、追加日志、**累加商品销量 + 扣减套餐库存**（库存扣减只发生在这里，是「下单不锁库存」导致的超卖风险根因）。

**④ `genDemoOrders()` — 演示数据生成**（`server.js:242`）
仅当 `orders` 为空时执行：生成 86 笔近 7 天订单，时间分布用 `Math.pow(random,1.7)` 制造「越近越多」；状态按当日/历史加权分布；账号按 `accountType` 生成符合格式的假数据；`accountType='none'` 时账号留空。启动时（`server.js:1053`）与后台「重置演示订单」均会调用。

#### 3.1.4 `overview()` — 看板聚合（`server.js:320`）

一次遍历内存数据算出全部指标，**无数据库聚合**：

- **卡片**：今日订单/销售额/毛利、累计营收/毛利、充值成功率（`success / (success+failed)`）、待处理数、人工工位数、通道余额合计、商品/通道/分类计数
- **趋势**：近 7 日按天分桶，输出 `{date, orders, amount, profit}`
- **分类占比**：仅统计 `success` 订单，通过 `product → category` 反查归类，其余进「其他」
- **通道健康度**：按 `supplierId` 统计结算订单成功率
- **低库存预警**：所有套餐展平后取 `stock < 100` 的前 6 条

#### 3.1.5 服务入口（`server.js:1030`）

```
createServer → OPTIONS 预检(204) / pathname 以 /api/ 开头 → handleApi，否则 serveStatic
  → 全局 try/catch 兜底 500（防单请求异常拖垮进程）
→ db.load() → genDemoOrders() → server.listen(PORT, HOST)
```

### 3.2 `lib/supplier.js` — 上游供货适配层（业务价值最高的模块）

**统一对接协议**（`supplier.js:1-14` 注释即协议文档）：上游只需实现「下单」「查单」两个接口。

| 函数 | 位置 | 职责 |
| --- | --- | --- |
| `buildSign(params, secret, signType)` | `supplier.js:39` | 过滤空值与 `sign` → key 字典序 → `k=v&k=v` → MD5 追加 `&key=secret` 取大写 / HMAC-SHA256 取大写 / `none` 返回空 |
| `buildSignRaw` | `supplier.js:52` | 输出签名原串（后台「测试连通性」给人核对用） |
| `request(cfg, url, body, isJson, timeoutSec)` | `supplier.js:59` | 原生 http/https 请求，`timeout` 事件触发 `destroy`，返回 `{status, raw, json}`，JSON 解析失败保留原文 |
| **`resolveSupplier(sku, product)`** | `supplier.js:105` | **选路策略**：仅取 `active` 通道 → ① `sku.supplierId` 显式绑定优先 → ② 按 `product.catId` 匹配 `supplier.categories`（空数组=不限）→ ③ 按 `priority` 降序取首个 |
| `seededRand(seed)` | `supplier.js:120` | `md5(seed)` 首 4 字节 → `[0,1]`，保证同订单同结果 |
| `isSandbox(supplier)` | `supplier.js:125` | `mode=mock/manual` 或全站 `settings.sandboxMode` 为真 → 沙箱 |
| **`submitOrder(order, supplier)`** | `supplier.js:136` | 主入口，返回 `{ok, status, supplierOrderNo, message, mode, cost, request?}` |
| `testConnection(supplier)` | `supplier.js:244` | 只构造参数 + 可选真实探测（调查单接口），不产生订单 |
| `parseCallback(body)` | `supplier.js:295` | 兼容 `outTradeNo`/`out_trade_no`、`status`/`orderStatus`、顶层/`data` 内嵌套三种写法 |
| `STATUS_MAP` | `supplier.js:21` | 上游状态 → 内部状态：`PENDING/PROCESSING→recharging`、`SUCCESS/DONE→success`、`FAILED/ERROR→failed`（**大小写与别名容错**） |

**`submitOrder` 的三条分支**：

```
① 无可用通道            → { ok:false, status:'failed' }「订单已转入待处理」
② mode === 'manual'     → { ok:true,  status:'recharging' }「进入客服处理队列」  ← 永不自动完成
③ skuCode 缺失          → { ok:false, status:'failed' }（防误派）
④ 沙箱（isSandbox）      → 确定性随机 + 空账号校验（accountType!=='none' 且账号空 → 失败）
                          + await min(delay,1500) 模拟网络耗时
⑤ 真实 API              → 组装参数 → 签名 → 最多 retry+1 次（失败退避 600ms×n）
                          → code!==0 视为业务失败直接返回（不重试，避免重复下单）
                          → 按 STATUS_MAP 映射状态
```

> 设计亮点：**重试只覆盖网络/解析异常，业务失败不重试**——这是防重复充值的正确取舍。

### 3.3 `lib/db.js` — JSON 数据层

| 函数 | 位置 | 要点 |
| --- | --- | --- |
| `load()` | `db.js:21` | 不存在 `db.json` → 从 `seed.json` 拷贝；**解析失败自动备份为 `db.json.broken-<ts>`** 并从种子重建；随后做**向后兼容补齐**（缺数组置空、缺 `settings/payConfig` 补对象、无管理员则注入默认 admin） |
| **`save()`** | `db.js:52` | 关键实现：`dirty` 标记 + `writing` 互斥 + `while` 重试（最多 50 次）→ **写 `.tmp` 再 `rename`（原子替换）**，避免写坏文件 |
| `get()` | `db.js:72` | 惰性加载单例，返回**内存对象引用**（调用方可直接改字段，靠后续 `save()` 持久化） |
| `uid(prefix)` | `db.js:78` | `前缀 + yyyymmddHHMMSS + 3 字节 HEX` |
| `addLog(action, detail, operator)` | `db.js:87` | `unshift` 到 `logs` 头部，超 800 条截断，内部自动 `save()` |

> 注意：**`get()` 返回引用 + 可变写**是全局约定——这是「零依赖小项目」的取舍，但也意味着任何模块都能改任意数据（无封装边界）。

### 3.4 `lib/payment.js` — 支付适配层

- `isSandbox()`：读 `payConfig.sandboxMode`（**默认 true**，即缺配置也是沙箱）。
- `createPayment(order)`：返回收银台信息 `{sandbox, tradeNo, payUrl, qrContent, message}`。
  - 沙箱：`payUrl → /pay.html?no=`，`qrContent → sandbox://pay?...`，前端二维码是**纯前端算法生成的装饰性图案**（`app.js:94 qrSvg`，FNV-1a + xorshift 伪随机，并非真二维码）。
  - 生产：按易支付风格拼 `pid/type/out_trade_no/notify_url/return_url/name/money` → key 排序拼串 + `merchantKey` → **MD5 小写** → 拼到 `apiUrl` 后的 query。
  - ⚠️ 生产分支的签名规则（直接追加 key、小写 MD5）与 `supplier.js` 的规则（`&key=`、大写 MD5）不一致，是历史遗留的差异，接入前需统一。

## 四、关键数据流（端到端）

### 4.1 正常购买链路（沙箱）

```
[首页] boot() → GET /api/store ────────────────▶ 渲染专区/商品/支付方式
  ↓ 点「立即购买」 openOrder(productId)
[下单弹窗 form] 选套餐/填账号/选支付
  ↓ 点「去支付」 submitOrder()
POST /api/orders ─────────────────────────────▶ 校验 → 建单(pending_payment) + charge.createPayment
  ↓ 返回 {order, pay}
[视图 cashier] cashierView() + startPolling()
  ↓ 点「模拟支付成功」 doPay()
POST /api/orders/:no/pay ─────────────────────▶ status=paid + 日志
                                                 └─ setTimeout 300ms → dispatch(order)
                                                      ├ resolveSupplier()  选路
                                                      ├ submitOrder()      沙箱：确定性随机
                                                      │   ├ status=success → markSuccess() 销量++/库存--
                                                      │   └ 其他           → scheduleSettle(3~5s)
                                                      └ 定时器到点 → markSuccess / status=failed
  ↓ 前端每 2.5s GET /api/orders/:no
[视图 result] resultInner() 渲染终态 + 处理日志时间线 + toast 提示
```

### 4.2 生产模式差异（关掉 `sandboxMode` 后）

| 环节 | 沙箱 | 生产 |
| --- | --- | --- |
| 支付 | 本地 `/pay.html` + 手动「模拟支付成功」 | `payment.createPayment` 拼易支付参数跳转真实收银台，回调 `POST /api/callback/pay` |
| 上游下单 | `seededRand` 确定性结果 | `supplier.submitOrder` 真实 HTTP（带签名、超时、网络重试） |
| 上游结果 | `setTimeout` 本地结算 | 上游回调 `POST /api/callback/supplier`；若上游只返回 PENDING 且不回调，**没有兜底对账任务**（见改进点） |
| 人工通道 | `mode=manual` 直接进 `recharging` | 同左，依赖后台「标记完成」 |

## 六、设计模式与编码规范

### 6.1 采用的设计模式

| 模式 | 落点 | 说明 |
| --- | --- | --- |
| **分层架构** | 表现层 → 接入层 → 业务层 → 数据层 | 单向依赖，数据层是唯一 I/O 出口 |
| **适配器 Adapter** | `lib/supplier.js`、`lib/payment.js` | 把「上游/网关的协议差异」收敛为统一内部接口 |
| **策略 Strategy** | `resolveSupplier()` 选路；`submitOrder()` 内 `api/mock/manual` 三分支；`isSandbox()` | 运行期按配置切换行为 |
| **装饰器 Decorator** | `decorate(order)` | 不侵入存储结构，按需派生展示字段 |
| **单例 + 仓储 Repository** | `lib/db.js` 模块级 `data` 单例 + `get()/save()` | 内存态为真源，落盘为快照 |
| **幂等设计（Idempotency）** | `markSuccess()` 提前 return；`/pay` 仅对 `pending_payment` 生效；`/api/callback/*` 重复回调只改一次 | 防重复扣库存/重复完成 |
| **确定性伪随机** | `seededRand(order.no + supplierId)` | 同订单结果稳定，便于演示与断言 |
| **模板方法 / View 分发** | `viewParts()`、`go(page)` + 渲染函数表 | 用查表取代 `if/else` 链 |
| **审计留痕（Audit Log）** | `db.addLog()` + 订单级 `order.logs[]` | 双粒度日志：全局操作日志 + 订单时间线 |
| **防御式开关（Feature Toggle）** | `sandboxMode`、`autoRecharge`、`deliveryMode`、`needConfirm` | 演示/生产、人工/自动可配置 |

### 6.2 编码规范（可观察到的团队约定）

1. **注释风格**：每个文件顶部有块注释说明职责；`server.js` 用 `/* ---- 分段 ---- */` 划区；关键业务函数用 JSDoc 标注返回结构（如 `submitOrder`）。
2. **命名**：变量/函数 `camelCase`；常量 `UPPER_SNAKE`（`STATUS_TEXT`/`MIME`/`STATUS_MAP`）；类 `PascalCase`（`CDP`）；HTML id 用 camelCase（`prodGrid`/`lgPass`）；CSS 类用 kebab-case（`prod-card`/`modal-mask`）。
3. **响应契约**：所有 API 返回 `{ ok: boolean, ... }`，失败为 `{ ok:false, message }`。前端 `api()` 统一解包后判 `res.ok`。
4. **错误处理**：服务端「路由层 catch 兜底 500 + 业务层 `fail(res, msg, code)` 显式返回」；前端「`if (!res.ok) return toast(...)`」早返回风格。
5. **不可变更新倾向**：更新实体用 `Object.assign(target, fields)` 白名单赋值，而非整体替换（避免丢字段）。
6. **安全基线**：所有用户输入进入 HTML 前 `escapeHtml()`；静态服务做路径前缀校验；请求体限制 2MB。
7. **前端事件方案**：`onclick="fn('id')"` 内联 + 全局函数，配合 `check-dom.js` 做定义性校验（弥补无模块系统带来的风险）。
8. **中文优先**：注释、UI 文案、日志、自检输出全部中文；自检脚本用 ANSI 颜色 + `✓/✗` 输出。
9. **改动护栏**：`tools/verify-patches.js` 用「关键字符串断言」固化某次改动的落点，属于团队自创的低成本回归保护。
10. **零依赖哲学**：宁可手写 CDP 客户端、手写 SVG 图表、手写二维码图案，也不引入 npm 依赖。

### 7.2 正确性与一致性

| # | 问题 | 说明 |
| --- | --- | --- |
| C1 | **下单不预占库存**，库存只在 `markSuccess` 时扣减 | 并发下单会把同一份库存卖出多次（`stock > 0` 的检查不具事务性）。建议下单即预占（`stock-- / locked++`），失败/关闭释放 |
| C2 | **无订单超时关闭任务** | `expireAt` 已写入、前端有倒计时，但服务端没有任何定时任务把过期 `pending_payment` 置为 `closed` |
| C3 | **无「充值中」对账兜底** | 若上游不回调或回调丢失，订单永久停在 `recharging`；README 也列为待办。需按 `queryPath` 轮询查单 |
| C4 | **定时器不持久化** | `scheduleSettle` 的 `setTimeout` 与服务重启解耦：重启后处于 `recharging` 的沙箱订单永久卡住 |
| C5 | **`readBody` 对非法 JSON 静默返回 `{}`** | 客户端错误体量下会退化成「参数缺失」的模糊报错，建议返回 400 + 明确信息 |
| C6 | **支付签名规则与上游签名规则不一致** | `payment.js` 用 `raw + key` + 小写 MD5；`supplier.js` 用 `&key=` + 大写 MD5。接入真实支付时需确认，勿混用 |
| C7 | **`markSuccess` 扣库存未做下界保护之外的补偿** | 退款（`refunded`）不回滚库存与销量，长期看统计会漂移 |
| C8 | **双份状态定义** | 后端 `STATUS_TEXT`（`server.js:19`）与前端 `STATUS_MAP`（`app.js:5`）需人工同步，建议由一处生成 |
| C9 | **`getOverview` 为全量内存遍历** | 单次 O(orders × 若干 map 查找)，订单到十万级会明显变慢；迁库后改聚合查询 |
| C10 | **`batch-dispatch` 串行 `await`** | 订单多时耗时线性增长，可用并发池（注意上游限流） |
